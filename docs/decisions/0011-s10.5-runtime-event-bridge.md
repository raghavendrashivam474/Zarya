# ADR 0011: S10.5 Explicit Runtime Event & Verification Bridge

## Context
Prior to S10.5, the frontend and Shefali's presence controller received limited runtime feedback (principally `terminal_output` logs after tool completion and voice stream state changes). The UI was forced to conservatively infer operational states using `deriveRuntimeState()`, resulting in inability to explicitly display verified success or failure states.

## Decision
We implemented a structured, unidirectional runtime event bridge over the existing WebSocket transport:
1. **Envelope Schema:** Standardized `runtime_event` envelope (v1) with `operation_id`, `timestamp`, `tool`, `state`, and `payload`.
2. **Authoritative State Mapping:** The bridge derives outcome state directly from S2/S3 verification payloads (`VERIFIED_SUCCESS`, `VERIFIED_FAILURE`, `UNKNOWN`).
3. **Epistemic Safety:** If a tool lacks an explicit verification payload or returns ambiguous results, the bridge guarantees state remains `UNKNOWN` — never manufacturing false confidence.
4. **Presence Integration:** `ShefaliPresence` consumes `runtimeState` to render calibrated, non-intrusive reactive visual overlays.

## Consequences
- **Positive:** Shefali's digital presence reflects authoritative runtime truth in real time without guessing.
- **Positive:** Zero regressions to S0–S10 execution and verification semantics.
- **Boundary Preserved:** Frontend remains a pure observer; execution authority remains strictly within Zarya's backend runtime.
