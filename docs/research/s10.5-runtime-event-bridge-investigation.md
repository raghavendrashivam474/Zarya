# S10.5 Runtime Event Bridge — Investigation Report

**Date:** 2026-09-14
**Branch:** zarya/s10.5-runtime-event-bridge
**Base:** v0.10.4 (df88628)

## Q1: Where does Zarya know work has started?
In server/index.ts, when Gemini issues a tool call matching DESKTOP_TOOLS.
The function call handler logs: `[Desktop Agent] Routing ${fnName} to Python backend...`

## Q2: Where does Zarya know a step has completed?
When callDesktopAgent() returns its HTTP response from agent/server.py /execute.
The result is an ExecuteResponse(ok, result, error, tool).

## Q3: Where is verification performed?
Inside individual Python tool handlers (agent/tools/*.py) using S2 verification fabric.
Results appear in result.verification.status as VERIFIED_SUCCESS/VERIFIED_FAILURE/UNKNOWN.

## Q4: Where is the final verification result available?
In the ExecuteResponse.result dict returned by agent/server.py.
Specifically: result.verification.status (when present).

## Q5: Where is S5 recovery reported?
In tool result payloads under result.recovery.status (RECOVERED/FAILED/UNKNOWN/NOT_ELIGIBLE).

## Q6: Where does server/index.ts receive runtime results?
In the callDesktopAgent() return value: { ok, result, error }.

## Q7: How does the frontend currently receive results?
Via WebSocket message type "terminal_output" — post-completion only, no intermediate states.

## Q8: Where does ShefaliPresenceController derive state?
In deriveRuntimeState() which maps (liveState, characterState, isToolRunning) to
RuntimePresenceState. Deliberately conservative — never returns VERIFIED_SUCCESS/FAILURE.

## Q9: Which runtime information is available but not transmitted?
- Verification status (VERIFIED_SUCCESS/VERIFIED_FAILURE/UNKNOWN) from tool results
- Recovery status from S5
- Work start/completion timing
- Operation identity

## Q10: Smallest bridge change?
Add broadcastRuntimeEvent() helper in server/index.ts that emits structured
runtime_event messages on the existing WebSocket before and after callDesktopAgent().
Inspect result.verification.status to determine outcome. Zero Python changes required.

## Architecture Decision
- Event emission at Node.js layer (not Python) due to synchronous HTTP architecture
- Existing WebSocket extended (no new connection)
- Frontend consumes explicit events, falls back to deriveRuntimeState() when absent
- UNKNOWN preserved verbatim — never inferred as success
- Backward compatible: terminal_output preserved alongside new runtime_event
