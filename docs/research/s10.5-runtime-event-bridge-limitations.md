# S10.5 Runtime Event Bridge — Limitations and Boundaries

**Date:** 2026-09-14
**Milestone:** S10.5
**Branch:** `zarya/s10.5-runtime-event-bridge`

## 1. Scope & Execution Boundary Limitations
- **One-Way Observability Only:** The event bridge flows strictly from Zarya Runtime → Server → Frontend → Shefali. The frontend does not send state assertions or execution requests via this bridge.
- **Node-Layer Event Timing:** Tool start and completion events are broadcast from the Node.js orchestration layer surrounding `callDesktopAgent()`. Because tool execution over HTTP is synchronous, fine-grained sub-step streaming from deep within Python tool functions is bounded to post-tool verification payload evaluation.
- **Epistemic Safety Default:** Tools that return `ok=True` but lack an explicit S2 verification dictionary default to `UNKNOWN` in the event bridge. They are never inferred as `VERIFIED_SUCCESS`.

## 2. Transport & Reliability Limitations
- **In-Memory WebSocket Transport:** Events are broadcast directly to connected WebSocket clients. There is no external broker (e.g. Redis, Kafka) or message queuing. If a client disconnects during execution, missed events are not replayed.
- **Non-Fatal Observability:** Failure to serialize or broadcast an event never interrupts or cancels the underlying desktop tool execution.

## 3. Data Minimization & Security
- Raw system secrets, environment tokens, and unrestricted screen capture bitmaps are excluded from `runtime_event` payloads. Payloads carry structured metadata (`ok`, `has_verification`, `tool`, `operation_id`, `state`).
