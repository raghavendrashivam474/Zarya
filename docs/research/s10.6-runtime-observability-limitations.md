# S10.6 — Runtime Observability Gaps & Limitations Audit

This document inventories the technical limitations of the S10.5 Runtime Event Bridge, classifying each gap by user impact, technical complexity, and priority.

## Gaps & Limitations Inventory

| Gap ID | Description | Technical Cause | User Impact | Priority | Recommendation |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **GAP-01** | Lack of Sub-step Progress Events during Multi-step Work | Python execution server processes /execute synchronously. No progress callbacks exist in the current bridge. | **MEDIUM** | **Evaluate** | Introduce lightweight sub-step event emission in S11, rather than a full SSE/Websocket rewrite. |
| **GAP-02** | Recovery Actions are Completely Invisible | Core recovery engine (ecovery.py) does not expose state hooks to the web server interface. | **LOW** | **Defer** | Keep recovery internal. Do not leak internal self-healing mechanics unless explicitly requested. |
| **GAP-03** | Lack of State Replay on Web Socket Disconnect | Web server does not maintain an event log per operation ID; reconnects default back to resting IDLE. | **LOW** | **Defer** | No action required. Web execution is synchronous; a disconnect implies a session failure. |
| **GAP-04** | Ambiguity of the UNKNOWN Visual State | The presence controller maps UNKNOWN to "uncertainty," which is difficult for non-technical users to parse. | **MEDIUM** | **Evaluate** | Refine frontend label mapping in src/components/presence/ShefaliPresenceController.ts without changing the internal schema. |
| **GAP-05** | Lack of Voice and Visual Timing Sync | Synthetic TTS plays asynchronously while Shefali's expression transitions instantly on WS event receipt. | **MEDIUM** | **Evaluate** | Synchronize audio session playback states with the visual presence state machine. |

## Architectural Decisions Deferred
1. **No Event Streaming Re-architecture:** We will NOT transition to Server-Sent Events (SSE) or custom protocol layers. The current WebSocket transport in server/index.ts is perfectly adequate.
2. **No Persistent Database / Analytics Warehousing:** Telemetry is bounded to development diagnostics and should never be persisted to disks or external services, preserving the privacy-first local architecture of Zarya.
