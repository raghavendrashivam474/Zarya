# S10.6 — Zarya Runtime Observability & Usage Evaluation

**Date:** 2026-09-14
**Milestone:** S10.6
**Base Commit:** f62527a (v0.10.5 Release)
**Status:** Completed Evaluation

---

## 1. Executive Summary
This document provides a rigorous, evidence-based assessment of Zarya's runtime observability, mapping how execution events flow from the core Python agent up to Shefali's user-facing presence. Per the S10.6 core principle (*"Observe before expanding"*), we evaluate what the system is currently capable of observing, where the true friction points lie, and whether granular substep streaming is an immediate necessity or a technical distraction.

---

## 2. Work Lifecycle Mapping

The table below outlines the visibility of each lifecycle stage across the layers of Zarya:

| Stage | Runtime knows? | Server knows? | Frontend knows? | Shefali can show? | Notes / Observability Status |
| :--- | :---: | :---: | :---: | :---: | :--- |
| **Intent** | Yes | Yes | Yes | Yes (LISTENING) | Captured via HTTP /intent request lifecycle and voice stream activation. |
| **Planning** | Yes | Yes | Partially | Yes (PLANNING) | Frontend infers from HTTP request state or voice state, but lacks step-by-step plan details. |
| **Authorization** | Yes | Yes | No | No | Strictly internal to Python backend; no WS events are broadcast. |
| **Execution** | Yes | Yes | Yes | Yes (WORKING) | Broadcast via WebSocket work_started event with state \WORKING\. |
| **Observation** | Yes | Yes | No | No | Internal to tool runtime. |
| **Verification** | Yes | Yes | No | No | Performed in Python backend prior to returning response. No distinct event. |
| **Recovery** | Yes | Yes (Implicit) | No | No | S5 closed-loop recovery runs synchronously inside Python backend. |
| **Outcome** | Yes | Yes | Yes | Yes | Broadcast via WebSocket \work_completed\ event with state \VERIFIED_SUCCESS\, \VERIFIED_FAILURE\, or \UNKNOWN\. |

## 3. Core Investigation Findings

### Area 1: Single-Step Work Lifecycle
An ordinary safe operation (e.g., executing a single file system read/write tool) transitions cleanly:
cls\text{IDLE} \xrightarrow{\text{work\_started}} \text{WORKING} \xrightarrow{\text{work\_completed}} \text{VERIFIED\_SUCCESS / VERIFIED\_FAILURE / UNKNOWN}cls
*Evaluation:* The 3.5-second overlay timeout for the success/failure state is sufficient for transient single-step feedback. It prevents visual noise during rapid sequences.

### Area 2: Multi-Step Work Visibility
Under the current synchronous Python agent boundary (gent/server.py handles /execute or /intent in a blocking thread), the frontend is held in the WORKING state for the entire duration of a multi-step workflow.
*Evaluation:* 
- For short multi-step actions (< 5 seconds), this is acceptable.
- For longer sequences (> 5 seconds), the lack of sub-step progress causes the UI to feel "frozen," which could erode user trust.
- *Conclusion:* Sub-step granularity is **partially** required. We do not need heavy streaming infrastructure, but a lightweight sub-step event boundary would significantly improve the user experience for complex actions.

### Area 3: Recovery Visibility (S5)
When a verification fails and recovery triggers, the backend blocks, attempts recovery, and only reports the final outcome. The user is completely blind to the fact that a recovery loop was executed.
*Evaluation:* 
- User-visible impact of this gap is **LOW**. 
- The user cares primarily about the final verified outcome. Showing internal self-healing sequences is technically interesting but does not materially improve user trust. In fact, showing frequent recoveries might make the system appear unstable or fragile.
- *Decision:* Keep recovery internal.

### Area 4: Epistemic Safety & UNKNOWN Presentation
When a tool does not provide explicit verification metadata, it cleanly maps to UNKNOWN.
*Evaluation:* 
- While code-level safety is 100% preserved (no false celebration), the user presentation of UNKNOWN is visually represented as "uncertain."
- *Friction:* The user does not easily distinguish between *"The task failed"* and *"The task succeeded, but Zarya could not independently confirm it."*
- *Recommendation:* The frontend should map internal UNKNOWN semantics to user-friendly messages like *"Action completed, but self-verification is not supported for this tool."*

### Area 5: Disconnect, Reconnect & Ordering Reliability
If the WebSocket disconnects during execution, the final work_completed event is dropped. Upon reconnecting, the frontend resets to IDLE state.
*Evaluation:*
- Because execution is synchronous, the HTTP execution call itself also fails or is disconnected, making the visual state reset natural.
- Multi-step state machine replay is not required because we do not run background autonomous worker pools.
